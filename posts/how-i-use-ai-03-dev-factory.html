03我如何使用 AI

透過 AI 打造開發流程，
實現開發產品的願望

當產品經理這些年，我從來不缺想法，缺的是把想法變成東西的手。AI 把想法與實現之間的距離縮到史上最短——但真的動手就知道，要「完整地」做出一個產品，還是沒那麼容易。這篇講我花掉最多時間的那件事：來回迭代出一條 AI 開發流水線。

一想法與實現，從來沒有這麼近過

當產品經理這些年，我從來不缺想法。缺的是把想法變成東西的手——過去任何一個像樣的產品，背後都是一支團隊和好幾個月的時間。想法很多，能排進資源裡被實現的很少，大部分連被驗證的機會都沒有。

AI 把這件事改寫了。現在，一個不寫 code 的人，有機會親手把產品雛形做出來。對產品人來說，這是很難不心動的時刻，而且我認為不該錯過——想法與實現之間的距離，從來沒有這麼短過。

不過說是這麼說，真的動手就知道：有了 AI，要把一個產品「完整地」做出來，還是沒那麼容易。從能動的雛形到經得起使用的產品，中間隔著品質、一致性、可維護性這些不性感的東西。所以我花掉最多時間的，其實不是做產品本身，而是研究和來回迭代「開發的工作流程」——這篇要講的，就是這條被迭代出來的生產線。

二我要的是成為 AI builder

為什麼捨得把最多的時間花在「流程」，而不是直接衝產品？因為我要的，從一開始就不只是某一個產品被做出來。這個系列第一篇提過，我把 AI 時代的功課分成三層：學習、使用、應用。前兩層說到底都還是「AI 幫我做事」；第三層的意思是親手把想法變成真的在運轉的東西。我給自己的目標就是走到第三層：成為一個 AI builder。

從這個目標看，「蓋一條生產線」就不是繞路，它本身就是目標的形狀——我要的是「我能重複地做出產品」這件事成立，而不是這一次運氣好。

剩下的問題只有一個：我這種不寫 code 的人，能成為哪一種 builder？答案藏在我最熟的事情裡：軟體公司能穩定出貨，靠的從來不是「有很會寫 code 的人」，是一套讓專業角色互相制衡的流程——規格有人審、設計有人挑戰、代碼有人驗、上線有人守門。而「設計讓一群專業角色協作出貨的流程」，正是 PM 的本業。我不需要變成工程師，我需要把一間軟體公司的組織，設計成 AI 的流水線。

三生產線長什麼樣

每個功能跑一輪 sprint（衝刺，軟體業的小批量開發循環），一輪裡 AI 扮演不同角色依序接力：規格 → 使用者體驗設計 → 技術架構 → 開發 → 視覺檢查 → 獨立 QA（品質驗證）→ 收尾歸檔 → 回顧。

圖 1｜八站流水線。從真實軟體公司抄來的三個設計：檔案交接（不憑記憶）、寫的和驗的分開（獨立 QA）、人只站在裁決點。回顧站的虛線是整條線最值錢的部分——教訓會寫回流程本身。

三個關鍵設計，都是從真實公司抄來的：

一、檔案交接，不憑記憶。每一站的產出是一份文件（規格書、設計稿、測試報告），下一站只認文件。這解決了 AI 最大的弱點——它不記得三天前的事，但它讀得懂三天前寫下的規格。

二、寫的和驗的，是不同的 AI。開發的 agent 和 QA 的 agent 是分開的，QA 拿到的是規格而不是實作說明——像真的公司一樣，不讓任何人自己改自己的考卷。品質不過關就退回重做，沒有商量。

三、人只站在裁決點。我出現在三種地方：方向對不對（規格關）、東西好不好看好不好用（視覺關）、這輪要不要收（收尾關）。判斷力是我唯一的稀缺資源，所以只花在只有人能做的判斷上。其餘時間，生產線自己跑。

這套流水線至今在兩個專案上跑了一百多輪 sprint：一個每天開盤真的在用的台股掃描工具（三千五百多個自動化測試守著它），和一個已經對外上線的求職產品。

四被真實世界打臉的兩課

第一課：機器測機器，有共同的盲區。求職產品上線前，有個 bug 在六輪測試裡都沒被抓到——直到我自己拿真實資料用，功能當場崩掉。事後回顧的結論很誠實：測試資料太乖了。AI 產的測試資料跟 AI 寫的解析邏輯，是同一種「規格思維」的產物，它們對彼此太客氣；真人講話不照規格來。品質關卡擋得住「沒照規格做」，擋不住「規格本身沒想到真實世界長怎樣」。

第二課：上線是另一個物種的考試。產品對外上線後不久就出了一次生產事故，整條流水線的守門都沒攔住——因為那類問題只在真實環境、真實流量、真實使用者的組合下才會出現。流水線能保證的是「做出來的東西符合規格」，「規格是否經得起真實世界」是另一門課。

圖 2｜流水線的管轄邊界。內圈的事（照規格做、測試通過）流水線管得死死的；但 bug 最喜歡住在內外圈之間——規格沒想到、只有真實世界才會出現的地帶。兩課都來自那裡。

五針對這兩課的 fine-tune

讓教訓自動回流。開頭說我花最多時間的是「來回迭代工作流程」——迭代的引擎就是這個：每輪 sprint 結束的回顧不是儀式，結論會寫回流程文件本身，下一輪的 AI 照新流程跑。那次六輪漏抓的 bug，回顧直接產出兩條流程修正提案。流水線最值錢的性質是這個：它會累積，一次學會的事不會再犯，這是單次對話永遠給不了的。

把真實資料放進生產線。測試資料太乖的解法，就是別再只用乖資料——我開始把自己的真實資料餵進測試，後來更進一步把自己變成第一個真實用戶。這件事引出了下一篇的故事：我把兩場真實面試押在自己的產品上。

還有一個誠實的補充：這條流水線到上個月為止，生產的都是給我自己用的工具。自己用，再嚴的標準都有折扣。所以求職產品從立項起就背著雙重任務——產品本身是一層，驗證這條流水線能不能從 0 到 1 做出真正對外上線的產品是另一層。畢業考的過程，下一篇講。

六給你帶走的：三條可搬走的設計原則

如果你也不寫 code 但想做產品，流水線的細節不必照抄，這三條原則可以直接搬：

  1. 角色分離、檔案交接——別讓一個 AI 從頭包到尾。拆成角色、用文件交接，AI 的健忘就不再是問題，而且每個角色可以被單獨要求品質
  2. 關卡而非信任——每一站設可檢查的過關標準，不過就退回。對 AI 的產出，「驗證」永遠比「信任」便宜
  3. 人只站在裁決點——你的判斷力是系統裡唯一不能量產的東西，把它花在方向、品味、取捨上，不要花在盯過程

最小起步版只有一步：把「寫的 AI」和「驗的 AI」分開——用兩個獨立對話，驗的那個只給規格、不給實作。光這一件事，就能超過絕大多數單次對話的品質。
